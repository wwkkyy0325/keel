# Open questions

The implementation session records ambiguous points here. The design session
answers them in the spec; do not guess.

| # | Question | Context | Decision | Date |
|---|---|---|---|---|
| 1 | How much of the profile schema must M1 parse? | `06-roadmap.md` asks the CLI to load a profile; `02-profile.md` assigns full schema resolution to M2. | M1 parses a minimal TOML subset and rejects unknown fields. Full validation lands in M2. | 2026-11-02 |
| 2 | Should the `evals/` skeleton exist at M1? | `03-modules.md` shows `evals/cases` and `evals/harness` in the M1 layout, but the same document forbids empty directories. | Defer `evals/` until M2 has real cases. | 2026-11-02 |
| 3 | What are the exact transitions for `Stalled`, `Escalating`, `WaitSubAgents` and `TerminalCommit`? | `01-kernel.md` names the auxiliary states but does not define their edges. | M1 implements a coherent table and tests every declared edge; revisit with an ADR when verification and subagents land. `WaitInteraction` was added by ADR 0003. | 2026-11-02 |
| 4 | Where do context stage priorities live? | `01-kernel.md` says the recipe carries stage priorities; `02-profile.md` says the profile selects stages and budget, while the `ContextStage` port already exposes `priority`. | M1 keeps priority on the stage implementation and the recipe carries names plus budget. Revisit if a second consumer needs per-profile priorities. | 2026-11-02 |
| 5 | How is `before_commit` honored when there is no commit target? | `02-profile.md` lists `commit`, `re-prompt` and `ask`; M1 has no repository or verification loop. | M1 accepts only `Commit`; `Reprompt` and `Ask` return `Unsupported` instead of being silently treated as commit. A re-prompt path arrives with verification. | 2026-11-02 |
| 6 | Which verification modes work before a verifier exists? | `02-profile.md` allows `none`, `evidence`, `tests` and `custom`; only `none` is reachable with the M1 mock. | M1 profiles use `none`; any other mode returns `Unsupported` instead of silently passing. | 2026-11-02 |
| 7 | Is `cargo-deny` available in the environment? | The verification gate requires `cargo deny check`, but the binary is not installed. | Installed `cargo-deny v0.20.2`; `cargo deny check` passes. Path workspace dependencies are pinned to `0.1.0` so the wildcard ban accepts them. | 2026-11-02 |
| 8 | Do interactions survive a process restart? | M1 keeps a paused turn in memory. A server or long-running host may need to resume later. | M1 uses in-memory pause/resume; persistent turn snapshots are M3 work. | 2026-11-02 |
| 9 | Which trash backend is authoritative? | M1 implements a workspace-local `.keel/trash` for deterministic tests and headless hosts. | Keep the `TrashStore` port; add the OS recycle-bin backend with `delete_file`. A failed backend never falls back to hard delete. | 2026-11-02 |
| 10 | How are scoped grants and session escalation revoked? | A user may allow one call, a path prefix, or the whole session. | Path-prefix grants and `FullAuto` escalation carry a TTL; `revoke_all` clears them. Command scopes and grant persistence remain. | 2026-11-02 |
| 11 | Where does strict per-action review live? | `manual` was removed as a permission level. | A host-level confirmation wrapper, not a kernel level; implement it with the CLI/frontend confirmation flow. | 2026-11-02 |
| 12 | How does each provider express interaction intents? | The kernel contract is `ModelChunk::Interaction`, but providers expose different wire mechanisms. | The OpenAI-compatible adapter uses the reserved `keel_interact` control tool and keeps the domain tool list unchanged. Other adapters decide independently. | 2026-11-02 |
| 13 | When does the acceptance checklist implementation land? | ADR 0004 defines the contract; M1 has no verifier. | M2 implements calculator, command, test and file-hash verifiers with the coding profile; M5 adds fault injection and human verification. | 2026-11-02 |
| 14 | How often is the context budget enforced? | M1 assembled context once and tool results could grow it past the budget. | The driver estimates the full message list before every model call; overflow ends the turn with `ContextOverflow` until the compaction ladder lands in M5. | 2026-11-02 |
| 15 | How are pasted secrets handled? | A user may paste a key into chat or a log may carry one. | Input is not blocked. The turn emits a `SecretWarning` event and returns the detected kind with the turn result, so the host shows the notice for that turn; test keys, hashes and config examples trigger the same patterns. The event log redacts detected secrets; `.env.example` is the supported place to fill credentials. OS keyring integration remains. | 2026-11-02 |
